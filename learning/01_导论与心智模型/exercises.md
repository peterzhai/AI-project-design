# 第 1 章 · 练习

> 完成方式建议：复制 `code/` 下的示例为新文件（如 `exercise_1.py`）在其上修改，
> 保持"结尾自检 + 可离线运行"的约定。

## 练习 1（热身）：给最小 Agent 加一个新工具

在 `run_minimal_agent` 不动一行代码的前提下，给 `TOOLS` 增加一个 `get_time` 工具
（返回固定字符串 `"2026-11-19 10:00 UTC+8"`），并构造 MockLLM 脚本，让模型
调用它后回答"现在是几点"。

**验收标准**：
- `run_minimal_agent` 与 `get_weather` 均未被修改；
- 模型调用 `get_time` 一次后给出最终答案；
- `llm.call_count == 2`。

**参考答案要点**：
- 这正是本教程的核心设计：循环对工具数量与内容无感知（依赖倒置）。
- 脚本示例：`[{"tool_calls": [{"name": "get_time", "arguments": {}}]}, {"content": "现在是 2026-11-19 10:00。"}]`。
- 若你的工具签名带默认参数，注意 Mock 脚本里 `arguments` 需要传齐必填参数。

## 练习 2（进阶）：把「保险丝」做得更智能

`run_minimal_agent` 的保险丝只看轮数。请改进为：**同一工具 + 同一参数连续调用 2 次
时提前终止**（提示：在循环里维护 `last_call` 元组做比较）。

**验收标准**：
- 对同一工具同一参数的重复调用，第 2 次触发时抛 `RuntimeError("疑似重复调用循环")`；
- 正常交替调用不同参数的工具不受影响。

**参考答案要点**：
- 记录 `(call.name, tuple(sorted(call.arguments.items())))` 作为签名。
- 这是真实 Agent 框架的常见护栏之一（loop detection），第 11 章会回到这个话题。
- 注意区分"第 2 次出现"与"第 1 次出现"：应当允许模型重试一次不同结果的场景（幂等判断是进阶方向）。

## 练习 3（挑战）：给 Agent 加"失败重试观察"

让 `ToolBox.execute` 在工具抛异常时**先重试 1 次**，两次都失败才返回错误观察。

**验收标准**：
- 工具第一次抛错、第二次成功时，观察结果是正常输出；
- 工具两次都抛错时，观察结果包含两次失败信息；
- 用 pytest 验证两种路径（可参考 `tests/test_ch01_examples.py` 中
  `test_toolbox_tool_exception_becomes_observation` 的写法）。

**参考答案要点**：
- 用 `for attempt in range(2)` 包住原调用逻辑；失败信息可拼接 `f"第{i+1}次失败: {exc}"`。
- 权衡讨论：无副作用工具（查询类）可以放心重试；有副作用工具（下单、发邮件）盲目重试会造成重复业务动作 —— 所以生产级实现要区分工具幂等性，这也是第 11 章"护栏"的前置思考。
- 更聪明的做法是把重试决策交给 LLM（把失败观察回传，让模型决定下一步），而不是代码里写死 —— 这正是第 5 章 ReAct 的思想。
