# 第 10 章 · 练习

## 练习 1（热身）：失败调用也要落盘

`TracedLLM` 目前只记录成功调用：内部 LLM 抛异常时记录丢失。请改进：
异常也生成一条记录（status="error"，error 字段存异常信息），然后**原样上抛**。

**验收标准**：
- 抛异常的调用也有 CallRecord（output_chars=0，含 error 信息）；
- 异常仍原样上抛（调用方感知不变）；
- pytest 断言记录数与异常类型。

**参考答案要点**：
- try/except 包住 inner.chat，finally 之外先 append 记录再 raise。
- 这是"追踪必须透明"的另一半：成功与失败都要留痕，故障排查才完整。

## 练习 2（进阶）：LLM 裁判评估器

断言式评估器处理不了"回答是否礼貌""解释是否易懂"。请实现 `LLMJudge`：
把「问题 + 答案 + 评分标准（1~5 分的说明）」交给一个裁判 LLM，输出 JSON
`{"score": int, "reason": "..."}`，用第 3 章 schema 校验器校验输出。

**验收标准**：
- 裁判输出不合法（缺 score/score 超范围）走修复闭环（复用第 3 章）；
- pytest 用 Mock 裁判覆盖打 3 分与打 5 分两种情况，断言 score/reason 被正确解析。

**参考答案要点**：
- 裁判也是 LLM，也会犯错：评分标准要写具体（什么算 1 分、什么算 5 分），
  并保留 reason 供人工抽查 —— 这就是"用 LLM 评 LLM"的可信度管理。
- 提醒：裁判调用本身也要计成本（进阶：把裁判消耗也纳入成本报表）。

## 练习 3（挑战）：回归对比报表（版本 A/B）

实现 `compare_runs(baseline: list[EvalResult], candidate: list[EvalResult])`：
- 按案例名对齐，输出每案例的通过状态变化（修复/退化/持平）与通过率变化；
- 任何"退化"案例（基线过、新版挂）单独标红列出，即使总通过率上升也要警告。

**验收标准**：
- pytest 覆盖三种变化（修复/退化/持平）；
- 存在退化时返回值带 warnings 列表，即使总通过率上升也要警告。

**参考答案要点**：
- 这是 CI 的思维：改版必须跑同一评估集，"总分离了但某个案例挂了"是危险的回归信号。
- 对齐用案例名作 key —— 所以 EvalCase.name 必须稳定（改名 = 新案例）。
