# 第 9 章 · 练习

## 练习 1（热身）：带置信度的路由

给 `Router.route_by_llm` 加置信度输出：Router LLM 除名字外再输出置信度（0~1），
置信度低于 0.6 时转"人工客服" Agent 兜底。

**验收标准**：
- 输出格式改为 `名字|置信度`（如 `退款专员|0.9`）；
- 低于阈值的任务路由给人工客服；
- pytest 覆盖高/低置信度两种情况。

**参考答案要点**：
- 输出契约变了就同步改解析（第 3 章的教训：schema 与解析一处定义）。
- "不知道就转人工"是多 Agent 系统最重要的安全阀之一 —— 不确定的分派比确定的错误更危险。

## 练习 2（进阶）：Worker 失败重派

`Orchestrator` 目前 Worker 失败（LLM 调用抛异常）会直接崩溃。请实现：
- `Worker.work` 捕获异常，返回结构化失败消息（`"执行失败: <原因>"`）；
- Orchestrator 收到失败产出时**重派一次**（最多 1 次），仍失败则该子任务标记失败；
- 汇总提示词中失败子任务标注"（该部分缺失，汇总时如实说明）"。

**验收标准**：
- 第一次抛错、第二次成功 -> 最终答案完整；
- 两次都失败 -> 汇总如实承认缺失（而非编造）；
- pytest 断言重派次数与最终 output。

**参考答案要点**：
- 这是第 2 章 `with_retries` 思想在协作层的延伸，但重试者是编排者而非调用栈 ——
  因为"换一个人试试"也是选项（可做进阶：重派给备用 Worker）。
- "汇总时如实说明缺失"防止模型在残缺输入上编造 —— 第 7 章诚实拒答的姊妹原则。

## 练习 3（挑战）：会议主持人（多轮协作协议）

实现 `MeetingAgent`：三个 Agent（产品/工程/设计）围绕一个议题各发言一轮，
主持人（第四个 LLM）读完全部发言后产出"决议 + 待办清单"。
要求用本章的 Blackboard 记录全部发言（key=发言者名），消息总线记录主持人
@每个人的"轮到你发言"通知。

**验收标准**：
- 三次发言全部落黑板，主持人汇总输入包含全部三人发言；
- 消息轨迹完整（3 条通知 + 顺序正确）；
- pytest 断言黑板条目数、消息顺序、决议引用了具体发言人。

**参考答案要点**：
- 会议 = 受控的多轮消息传递 + 一次汇总，协议越显式越不容易乱。
- 进阶讨论：辩论式（相互反驳）与合作式（互不评论）协议的优劣 ——
  前者更深入但更贵且可能发散，第 10 章评估会提供量化手段。
