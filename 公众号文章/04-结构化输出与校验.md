## 一个深夜事故

先讲一个我入行以来印象最深的事故。

项目联调期，有个功能是"用户提问 → 模型判断问的是知识还是数据 → 走对应流程"。逻辑很简单，演示了几十次都没问题。

某个周五深夜，值班同事收到告警：一条提问被路由错了，本该去查数据库的"今天一车间产量"，被当成知识问题去检索文档，最后答非所问地回了一段报工规程。

第二天复盘，根因让人哭笑不得：那晚模型返回的 JSON 里，路由字段不是约定的 `"data"`，而是——**`"数据查询"`**。它"贴心"地把枚举值翻译成了中文。

而当年的代码是这样处理异常的：解析 JSON，取到字段，发现不认识，**默认当作知识问题处理**。

看出来了吗？代码里藏着一句没人写出来过的话：*"遇到不认识的路由，就当知识问题吧。"* 对绝大多数输入，这个兜底碰巧是对的——所以演示一直很顺。直到那个周五的深夜，它碰巧错了。

这个事故教会我一件事：**模型输出的解析代码，写的不该是"期望的路径"，而是"所有可能出错的路径"。** 今天这篇，就把这个认知展开讲透。它可能是全系列最不性感、但最重要的一篇。

## 为什么需要结构化输出

回顾一下我们走到哪了：第一篇认识了 LLM 这个零件，第二篇拆开看了它的生成原理，第三篇学会了工程化调用。但到目前为止，模型说的都是"人话"——一段自然语言文本。

而系统里，模型输出是要被**程序**消费的：

```
用户提问 ──▶ 模型判断 ──▶ {route: "data"} ──▶ 程序分支 ──▶ 走数据查询
```

程序不认识"我觉得这个问题应该去查数据库"，程序只认识 `{"route": "data"}`。

**从这一篇起，模型的角色开始变了：它不再只是"回答者"，开始兼任"决策者"和"填表员"。** 而只要模型承担决策职责，它的输出就必须是机器可解析、可校验的。这是从"聊天应用"跨到"Agent 系统"的第一道门槛。

## 概念：结构化输出的三个层次

让模型输出"机器话"，工程上有三个逐级递进的层次。

### 层次一：提示词里"求"它

最朴素的办法，在提示词里写清楚格式要求：

```
请判断用户问题的类型，只输出 JSON，格式：
{"route": "knowledge" | "data" | "clarify", "reason": "一句话理由"}
```

有效，但不可靠。模型偶尔会给 JSON 加个开场白（"好的，以下是判断结果："），偶尔用中文引号，偶尔在结尾加个句号——每一个都能让 `json.loads` 当场炸掉。

记住第一篇的认知一：**模型是概率式的。** "只输出 JSON"是一个请求，不是约束。概率式的东西，就没有 100%。

### 层次二：API 层的 JSON 模式

于是各家 API 提供了 `response_format: {"type": "json_object"}` 这类开关（本系列的调用代码第三篇已经见过——网关里的 `structured=True` 参数就是干这个的）。打开后，模型被约束为**只能输出合法 JSON 语法**。

这一层解决了"语法合法"，但解决不了"语义正确"：

- 字段名可能不对（`type` 还是 `category`？）
- 枚举值可能不对（`"data"` 还是 `"数据查询"`？——对，就是深夜事故的那个坑）
- 字段可能缺失（`topic_id` 忘了输出）

语法是格式问题，语义是内容问题。**API 层的 JSON 模式管不住内容。**

### 层次三：Schema 校验——程序接住的最后一道关

真正可靠的做法，是给输出加上**运行时校验**：先定义好"输出的正确长什么样"（schema），模型输出后先过校验，**过了才往下走，不过就不过**。

Python 生态里标准答案是 Pydantic——用类型注解声明结构，一行代码完成校验：

```python
from pydantic import BaseModel, field_validator

class Route(BaseModel):
    route: Literal["knowledge", "data", "mixed", "clarify"]
    question: str
    topic_id: str | None = None
    sequential: bool = False
    clarification: str = ""
```

这份 schema 声明了：`route` 只能是四个枚举值之一；`question` 必须是字符串；`topic_id` 可有可无，有就必须是字符串……任何一条不满足，Pydantic 当场抛出 `ValidationError`，**而不是让一个畸形数据流进系统**。

对照真实项目，它的路由结果定义就长这样（字段比我这个简化版多几个，本质相同）——一行类型注解，就是一道闸门。

## 动手：把一句话变成结构化数据

目标：输入"今天一车间产量是多少？"，模型输出一个**校验通过**的 `Route` 对象。包含完整的事故防御。

```python
"""structured_output.py —— 模型输出的解析与校验闭环"""
import json
from typing import Literal

from openai import OpenAI
from pydantic import BaseModel, ValidationError

client = OpenAI(
    base_url="https://open.bigmodel.cn/api/paas/v4",  # 换成你的服务商
    api_key="你的KEY",
)
MODEL = "glm-4.7"  # 换成你的模型名


# ① 先声明“正确的输出长什么样”——这是程序与模型之间的契约
class Route(BaseModel):
    route: Literal["knowledge", "data", "mixed", "clarify"]
    question: str
    clarification: str = ""


ROUTER_PROMPT = """你是工厂助手的路由器。判断用户问题类型，输出 JSON。

规则：
- route 只能取以下值之一：
  knowledge：问操作规程、制度、知识类问题
  data：问产量、库存等实时数据
  clarify：问题说不清楚，无法判断
- question：把用户问题补全为完整、独立的问题
- clarify 时，clarification 填一句要反问用户的话

只输出 JSON，不要输出其他任何内容。"""


def route_question(question: str) -> Route:
    messages = [
        {"role": "system", "content": ROUTER_PROMPT},
        {"role": "user", "content": question},
    ]
    resp = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        temperature=0,
        response_format={"type": "json_object"},  # 层次二：语法约束
    )
    raw = resp.choices[0].message.content

    try:
        data = json.loads(raw)        # JSON 语法解析
        return Route.model_validate(data)  # 层次三：schema 校验
    except (json.JSONDecodeError, ValidationError) as exc:
        # ③ 铁律落点：校验失败 → 终止本次运行，记录现场，绝不猜测
        print(f"[路由失败] 原始输出：{raw!r}")
        print(f"[校验错误] {exc}")
        raise RuntimeError("路由输出不合法，本次运行终止") from exc


if __name__ == "__main__":
    for q in [
        "今天一车间产量是多少？",        # data
        "MES 怎么报工？",               # knowledge
        "那它呢？",                     # 说不清 → clarify
    ]:
        print(f"\n问题：{q}")
        result = route_question(q)
        print(f"路由：{result.route}")
        if result.clarification:
            print(f"反问：{result.clarification}")
```

跑起来，三个问题应该分别命中 `data`、`knowledge`、`clarify`。然后强烈建议做两个"破坏性实验"：

1. **去掉 `response_format` 参数**再跑几次：观察模型输出 JSON 前后偶尔出现"杂物"（开场白、markdown 代码块标记），以及 `json.loads` 如何当场炸掉——体会层次一为什么不够
2. **手动喂脏数据**：把 `Route.model_validate({"route": "数据查询", "question": "x"})` 单独跑一下，看 Pydantic 报出完整清晰的错误清单——**这正是深夜事故里，那晚缺失的一道关**

## 进阶视角：一条铁律的分量

教程到这里，结构化输出似乎已经闭环了。但真实项目里还有更深一层的问题：**校验失败之后，到底该怎么办？**

### 业界常见的三种做法

1. **静默兜底**（深夜事故的元凶）：解析失败就走默认分支。看似"稳"，实则是把不确定性藏进系统，等一个最坏的时机爆发
2. **无限重试**：失败了就把错误信息塞回模型，让它改。有次数限制的重试是合理的；但无限重试 = 无限成本，而且**连续失败往往意味着提示词或 schema 设计有问题**，重试治不了根
3. **终止并记录**：校验失败 → 结束本次运行 → 记录原始输出与错误 → 返回一句诚实的"我暂时处理不了这个问题"

那个工厂项目选的是第三种，并且把它写成了团队纪律：

> **不猜测执行：任何模型结构化输出，必须先过 Pydantic 校验；校验失败，结束运行、记录失败，不重试硬猜。**

为什么这么"轴"？因为算过账：

- **错误成本不对称**。路由错了，用户拿到的是答非所问（信任崩塌）；多问一次"您是想问规程还是产量？"，成本几乎为零。宁可礼貌地停，不可自信地错
- **可观测优先**。每一次校验失败都被记录成结构化日志，攒起来就是提示词优化的第一手材料。静默兜底恰恰会把这些信号全部吞掉——**你修不了你看不见的问题**
- **它逼着你认真设计契约**。知道"过不了就死"，你自然会把枚举值定义得干净、把提示词写得没有歧义。校验是纪律，更是设计压力

### 顺势预告：这条铁律如何贯穿全系列

"不猜测执行"是那个项目所有模型交互的公共底座，后面每一篇你都会遇到它的变体：

- **路由阶段**（本篇）：路由值不在枚举内 → 终止
- **查询计划阶段**（第 13 篇）：模型填的查询表单里有白名单之外的字段 → 终止。模型永远只能"选"，不能"造"
- **回答阶段**（第 07 篇）：检索证据不足 → 不硬答，反问澄清。**宁可少答，不可编造**

回头看，这其实是第一篇"认知一"的最终归宿：**模型是概率式的，所以系统的每一道边界都必须由确定性的代码把守。** 模型负责"尽量对"，程序负责"绝不容忍错"——这个分工，就是 LLM 应用工程的全部要义。

## 小结

1. 模型输出要被程序消费，就必须结构化 + 校验：**提示词约束（请求）→ JSON 模式（语法）→ Schema 校验（语义），三层缺一不可**
2. 深夜事故的教训：静默兜底会把不确定性藏进系统，在最坏的时机爆发；**解析代码要写"所有可能出错的路径"**
3. 一条值得抄走的铁律：**校验失败，宁可终止、不可猜测**——错误成本不对称，且失败记录是提示词优化的第一手材料
4. 模型负责"尽量对"，程序负责"绝不容忍错"

到这里，第一章"认识零件"完结。我们有了正确的心理模型（概率式、无状态、有截止）、会工程化调用（消息、token、流式）、能让程序可靠接住模型输出（结构化 + 校验 + 铁律）。
