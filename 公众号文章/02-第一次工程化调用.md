## 一个意外的发现

上一篇结尾留了个钩子：**模型没有记忆，那网页版的连续对话是怎么回事？**

先讲一个真事。

项目初期，我们做需求演示，给车间的班组长们看对话效果。有位老师傅问完一个问题，跟着追问了一句"那第二条是什么意思？"。模型答得很好。老师傅点点头，然后问了我一个让我愣住的问题：

"这玩意儿是不是一直在偷偷录音？"

我解释了半天"它没有在录任何东西"。回家路上我想明白了——**普通人感受不到"无状态"这件事，恰恰说明网页应用把'记忆的错觉'做得太好了。** 而作为开发者，我们必须亲手戳破这个错觉，才知道系统真正的骨架长什么样。

这一篇，我们把 ChatGPT 网页版"扒开"，用 50 行 Python 写一个有连续对话能力的命令行助手——也就是把网页版最核心的那层机制，亲手造一遍。

## 消息列表：与模型对话的唯一方式

工程上调用 LLM，全世界主流的接口长得都差不多，核心就是一个**消息列表**发过去：

```python
response = client.chat.completions.create(
    model="glm-4.7",
    messages=[
        {"role": "system", "content": "你是一个工厂助手。"},
        {"role": "user", "content": "MES 怎么报工？"},
        {"role": "assistant", "content": "（上一轮的回答……）"},
        {"role": "user", "content": "那第二条是什么意思？"},
    ],
)
```

三种角色，各司其职：

- **system**：设定。你是谁、什么风格、什么边界。用户看不见，但影响每一次回答。它是"人设"的工程化身
- **user**：用户说的话
- **assistant**：模型之前的回答。**注意：这个字段就是"记忆"的真相**——所谓历史，就是我们自己抄下来、下次再发回去

所以"连续对话"的完整机制是：

> 每轮对话后，把新的问答追加进消息列表；下一次提问时，**把从头到尾的完整列表整体重发**。模型看到的每次都是一部"完整的剧本"，它只是在接着写下一句。

模型不是记住了你，是你每次都把剧本重新递给它一遍。第二篇到这一步，上一篇的悬念解开了。

这里埋一个后面会反复出现的工程话题：**消息列表越长，token 越多，费用越高、延迟越大**。第一篇说过上下文窗口有上限——历史不可能无限追加。什么时候裁、怎么裁、裁坏了会怎样，是第八篇的主菜，这里先按下。

## Token：模型的计量单位

聊计费绕不开 token。**token 是模型处理文本的最小单位**，不等于"字"也不等于"词"——粗略体验：1 个汉字约 1–2 个 token，1 个英文单词约 1 个 token。

关键认知是：**计费和限制，都按 token 算，而且分两头算**。

- 输入（prompt）+ 输出（completion）都计费，输出通常比输入贵数倍
- 历史每追加一轮，下一轮的输入 token 就多一截——**对话越长，每一轮越贵**，这就是所谓的"长对话变贵"，是指数式的，不是线性的

这个成本结构直接决定了后面一堆架构：为什么 RAG 只检索相关段落而不是塞全部文档（第 06 篇）、为什么上下文要裁剪（第 08 篇）、为什么路由要把简单问题分给便宜的小模型（第 09 篇）。**在 LLM 应用里，token 就是弹药，架构就是省弹药的艺术。**

另外记住 `response.usage` 字段，它返回这次调用实际消耗的 token 数。上线后盯住它，是成本控制的第一现场（第 17 篇还会回到这里）。

## 流式输出：不是炫技，是体验刚需

网页版那种"一个字一个字往外蹦"的效果，不是模型在前端打字——是**服务端在一边生成一边往外送**。

原理一句话：模型本质上是逐 token 生成的（还记得"下一个词预测器"吗），所以服务端不必等全文生成完，每生成一小段就推给客户端，客户端边收边显示。

注意两个细节：

- **总 token 不变，总时间基本不变**（甚至可能略快）。流式省的是"用户看到第一个字的时间"（首 token 延迟），不是总时长。但体验上是质变——3 秒的空白等待和 3 秒的打字机，用户感受完全不同
- **工程上，流式的复杂度远高于一次性返回**：断线怎么办？中途出错已输出的内容怎么办？能否取消？真实项目里，回答是流式的、事件是结构化的，一套 SSE 事件协议就是为这些边界情况设计的——第 16 篇展开

## 动手：50 行命令行助手

把上面的认知拼起来。目标：一个能连续对话的命令行助手，流式输出，随时 `exit` 退出，Ctrl+C 可安全中断。

```python
"""chat_cli.py —— 50 行的连续对话助手（含流式输出）"""
import sys
from openai import OpenAI

client = OpenAI(
    base_url="https://open.bigmodel.cn/api/paas/v4",  # 换成你的服务商
    api_key="你的KEY",
)
MODEL = "glm-4.7"  # 换成你的模型名

SYSTEM_PROMPT = (
    "你是华兴精密的厂内助手。回答要准确、简洁、口语化，"
    "不懂就直说不懂，禁止编造厂内流程和数据。"
)


def chat_loop() -> None:
    print("厂内助手已启动（输入 exit 退出）")
    # “记忆”的全部真相：一个我们自己维护的消息列表
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]

    while True:
        try:
            user_input = input("\n你：").strip()
        except (KeyboardInterrupt, EOFError):
            break
        if not user_input or user_input.lower() == "exit":
            break

        messages.append({"role": "user", "content": user_input})
        print("助手：", end="", flush=True)

        try:
            # 关键：stream=True，逐段收取生成中的文本
            stream = client.chat.completions.create(
                model=MODEL, messages=messages, stream=True,
            )
            reply = ""
            for chunk in stream:
                delta = chunk.choices[0].delta.content or ""
                if delta:
                    reply += delta
                    print(delta, end="", flush=True)
            print()
        except KeyboardInterrupt:
            print("\n（已中断本次回答）")
            # 被打断的回答不完整，从历史里剔除，避免污染下一轮
            messages.pop()
            continue
        except Exception as exc:
            print(f"\n[调用失败] {exc}")
            messages.pop()  # 失败这轮不入历史
            continue

        # 完整回答追加进历史，下一轮整体重发——这就是“连续对话”
        messages.append({"role": "assistant", "content": reply})


if __name__ == "__main__":
    chat_loop()
    print("再见。")
    sys.exit(0)
```

跑起来后，重点做三个实验：

1. **追问实验**：问"MES 怎么报工"，再追问"那第二条是什么意思"。它答得上来——因为第二轮请求里，第一轮的完整问答就在 `messages` 里。**"记忆"就是我们这几行代码制造的**
2. **中断实验**：回答打到一半按 Ctrl+C。注意代码里 `messages.pop()` 的处理——被截断的回答如果不剔除，下一轮模型会接续一段"半截话"，行为很诡异。这是流式带来的第一个真实工程问题
3. **成本实验**：把 `stream=True` 换成普通调用，加打 `response.usage`；多聊几轮，观察 `prompt_tokens` 怎么随着对话变长而增长

这 50 行代码，就是 ChatGPT 网页版最核心的骨架（当然，人家外面还包了几十层）。别小看它——**把它吃透，你已经理解了 LLM 应用的地基。**

## 进阶视角：真实项目里的模型调用

教程里 `pip install openai` 一把梭，但到了真实项目，第一次模型调用就会遇到一个尴尬的问题。

### 问题：内网环境与"模型还没到位"

那个工厂项目是部署在客户内网的：没有公网、模型服务由甲方后期采购、接口规格迟迟定不下来。而团队的开发不能停——路由、RAG、权限、编排，每一块都要调，每一块都依赖"有一个模型在"。

怎么办？等项目？项目就死了。

### 解法：模型网关 + 模拟模型

该项目做法：**在业务代码和模型服务之间，放一个"网关"层，定义最小协议**——业务代码只依赖这个协议，不依赖任何一家的 HTTP 格式：

```python
class ModelGateway(Protocol):
    async def complete(self, messages, *, structured=False) -> str: ...
    def stream(self, messages) -> AsyncIterator[str]: ...
    async def embed(self, texts) -> list[list[float]]: ...
```

就三个方法：补全（可要求 JSON）、流式、向量化。然后给网关做两个实现：

- **真实现**：OpenAI-compatible 适配器，读配置里的 base_url、模型名、密钥，对接内网推理服务
- **模拟实现**：一个**确定性模拟模型**——用规则和哈希向量返回可预期的结果，回答明确标注"这是模拟回答"

于是开发的节奏变成：**协议先行，模拟先行，模型后补**。等甲方模型到位，改一行配置，业务代码零改动。（这个模拟模型还藏着一个大坑，第 17 篇讲验收时再摊开。）

这个思路值得展开一句：**面向协议编程，而不是面向具体服务编程**。你在业务代码里直接写死 `openai.chat.completions`，就把整个系统焊死在一家服务上；依赖自己定义的 `ModelGateway`，供应商是可替换的零件。后面 RAG 的向量库、数据库，都会反复用这招。

### 另一个细节：temperature

你可能注意到，真实项目的网关里写的是 `temperature: 0`。

temperature 控制"下一个词"的采样随机性：**调高，答案更多样、更有创意；调低，答案更确定、更可复现**。

那什么时候要高、什么时候要低？判断标准一句话：**看你的下游是"人"还是"程序"**。

- 下游是程序（我们要解析它的输出、要做路由判断、要填查询表单）→ 用低温甚至 0，**要的是可复现**
- 下游是人（写文案、想点子、闲聊）→ 适度调高，要的是多样

工厂助手整个链路里，模型输出全部要被程序消费，所以全线低温。这也是第一篇"认知一"的工程落地：概率式的大脑，在系统里要被"锁"到最稳的那一档。

## 小结

1. 连续对话的真相：**应用层维护消息列表，每轮整体重发**。所谓记忆，是我们亲手制造的错觉
2. token 是计量单位和成本单位，两头计费、长对话指数变贵——**架构就是省弹药的艺术**
3. 流式输出省的是"首字延迟"不是总时长，但带来中断、错误处理等真实工程问题
4. 进阶：真实项目用**协议网关 + 模拟模型**解耦内网模型依赖；下游是程序就用低温，要可复现

下一篇，迈出从"聊天"到"干活"的关键一步：模型说的终究是"人话"，程序怎么可靠地接住？——结构化输出与校验，以及一条铁律：**校验失败，宁可终止，不可猜测。**
