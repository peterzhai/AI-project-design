# 01 · 从 LLM 到 AI Agent（一）：目标与路线

---

（系列第 1 篇 · 约 6 分钟读完）

## 目标

做一个 AI Agent 的基础底座，以工厂需求为切入点。

场景很具体：一家制造企业，两个车间，三千多页内部操作规程，一套跑了八年的 MES。要给员工做一个助手，让大家用自然语言完成日常工作里最高频的两件事——问规程、查产量。

## 要解决的三个问题（过程中需要解决的问题可能会越来越多）

**知识问答**。规程全堆在共享盘里，老师傅凭经验找，新员工靠问人。要让助手直接回答"MES 怎么报工"这类问题，答案必须来自厂内文档、可溯源、带引用。

**数据查询**。"今天一车间产量是多少"——现在要登 MES、找菜单、点筛选。要能直接问自然语言，但模型不能直接碰数据库：查询必须受控、只读、可限制。

**权限管理**。一车间的产量不能让二车间看见。权限必须从架构上保证，而不是靠模型自觉。

这三个问题分别对应 Agent 底座的三块核心能力：检索增强（RAG）、工具调用（Function Calling）、权限体系。也是这个系列的主线。

## 如何执行

不空谈概念，以一个工厂智能问答系统作为实践项目，边拆解边动手：

- **第一、二章拆零件**——先把 LLM 调用、结构化输出、工具、RAG、记忆这些基础件逐个吃透，每个都配上最小可运行代码
- **第三章组装**——路由、编排、串并行，把零件拼成系统，并回答"这到底算不算 Agent"
- **第四章落地**——受控查询、权限、持久化、交付、上线，跨过 demo 与生产的距离

每篇的结构固定：问题 → 原理 → 动手代码 → 真实项目里的做法与取舍。

## 首先得知道LLM 是什么东西，是怎么工作的（这里不深入讨论，只简单介绍）

一切架构决策，都得从 LLM 的工作原理推出来。四条基本事实：

**它是概率式的。** 本职工作只有一件事：给定前文，预测下一个 token。它是概率的，不是检索的——不查资料，算概率。推论：幻觉不是 bug，是原理的副产品，提示词根治不了，只能靠架构（让模型只基于喂给它的证据说话）。

**它是无状态的。** 每次 API 调用都是全新计算，模型不记得上一句。网页版聊天的"连续感"，是应用层每次把完整历史重发一遍制造的错觉。推论：记忆是应用层工程，不是模型能力。

**窗口有限。** 单次调用能容纳的 token 有上限，而且塞得多不等于学得会。推论：三千页规程不能硬塞，要用检索按需取用。

**知识有截止。** 训练数据有时间边界，厂内私有数据、实时数据一概不知。推论：私有知识靠 RAG，实时数据靠工具。

一句话总结：LLM 是一个见多识广、会推理、会表达，但没有记忆、没有手脚、知识有保质期的大脑。我们要做的不是训练更聪明的模型，而是给它配上四样东西：

| 缺什么 | 补什么 | 在哪篇 |
|---|---|---|
| 私有知识 | RAG 检索 | 06–07 |
| 手脚 | 工具调用 | 04–05 |
| 记忆 | 会话管理与持久化 | 08、15 |
| 不可靠 | 校验、路由、权限 | 03、09、13–14 |

配上之后的东西，才叫 AI Agent 系统。
